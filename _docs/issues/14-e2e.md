## Goal

The acceptance scenarios are proven in a real browser with three users, not
only in unit tests.

## Acceptance criteria

- [ ] Playwright is configured for Chromium with one worker and a fresh
      database per run.
- [ ] `make e2e` builds and starts the Compose stack, waits for `/healthz`, runs
      the suite, and tears the stack down.
- [ ] `E2E_BASE_URL` runs the same suite against an already-running environment.
- [ ] The main test uses three browser contexts: host, guest A, and guest B.
- [ ] Host signs up and creates a capacity-1 session; A books and sees
      Confirmed; B sees Waitlisted, position 1.
- [ ] A cancels; B sees Confirmed within one polling interval (use a bounded
      poll, not a fixed sleep).
- [ ] Host checks B in; B sees Checked in and the host roster reflects it.
- [ ] A signed-in non-host receives 403 when calling the check-in endpoint.
- [ ] Duplicate booking and a missing CSRF header return the documented
      errors.
- [ ] Failure artifacts include a trace, screenshot, and video; CI uploads
      them.
- [ ] The suite passes twice in a row from a fresh database.
- [ ] A CI job runs the suite after the image build and blocks the dev deploy on
      failure.

## Out of scope

- Firefox and WebKit.
- Visual regression and load testing.
- Testing against production.

## Constraints

- Tests in `e2e/`; no product code changes solely to make a selector easier
  unless the change improves accessibility.
- Use role, label, and text selectors; avoid brittle CSS selectors.
- Use unique emails per run (`Date.now()` or a UUID).
- No `waitForTimeout` except inside a bounded polling helper.
- Do not share cookies between contexts.
